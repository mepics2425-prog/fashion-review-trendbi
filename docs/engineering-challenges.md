# Engineering Challenges

다음은 사용자 제공 업무 경험을 바탕으로 정리한 사례다. 운영 소스·로그·DB는 가져오지 않았다. 공개 저장소의 검증은 독립적으로 작성한 합성 fixture에 한정한다.

## Case Study 01 · Reliable Review Count Extraction

**Problem.** 일부 상품에서 정확한 리뷰 수를 얻지 못했다. 확인 불가를 0으로 저장하면 이후 급증처럼 보이는 가짜 트렌드가 만들어질 수 있었다.

**Root Cause.** `__NEXT_DATA__`만으로 항상 정확한 `reviewCount`를 확보할 수 없었다. 페이지에 여러 숫자나 상품 객체가 존재할 때 필드명만 탐색하는 방식은 요청 상품과 무관한 값을 채택할 위험이 있다.

**Solution.** JSON-LD의 `Product.aggregateRating.reviewCount`를 보조 소스로 사용했다. 요청·응답 상품 URL, 상품 식별 일치, Product 객체 여부, 리뷰 수 후보의 유일성을 검증했다. 모호한 값·잘못된 상품을 제외하고 검증된 값만 DB에 적재했다. 추출 실패는 결측으로 남겼다.

```text
requested product → response identity matches?
  → JSON-LD Product with matching identity?
    → one consistent nonnegative integer reviewCount?
      → store verified count (including 0)
    otherwise → missing / error classification
```

**Validation.** 업무에서는 실패했던 일부 상품을 재조회해 값을 정상 확인했다는 사용자 제공 이력이 있다. 전체 성공률의 개선 폭은 측정 근거가 없어 제시하지 않는다. 데모의 [오프라인 추출 계약](../src/review_extractor.py)과 [테스트](../tests/test_review_extractor.py)는 0, 중복 일치 후보, 충돌 후보, 잘못된 상품·도메인·값을 검증한다. 실제 사이트에 요청하지 않는다.

**Trade-offs.** 엄격한 검증은 일부 정상 상품도 결측으로 남길 수 있다. 잘못된 성공보다 명시적인 실패를 선택한 설계다. 공개 구현은 URL 식별이 가능한 제한된 JSON-LD 형태만 지원한다. 현재 무신사 페이지의 전체 구조·리다이렉트·렌더링 호환성까지 검증한 수집기가 아니다.

## Case Study 02 · Category-balanced Observation Scheduling

**Problem.** 특정 카테고리에 관측이 집중되면 수집량이 많아도 카테고리 간 비교에 필요한 이력이 부족했다.

**Root Cause.** 수집 접근성이 높은 상품이나 자주 등장하는 상품을 반복해서 고르면 기존 편중이 유지된다. 최신값 갱신만으로는 여러 날짜에 걸친 비교 표본이 쌓이지 않는다.

**Solution.** 오전 9시에는 카테고리별 검색어를 순환했다. 오후 1시 재관측은 하루 최대 20개, 상의·하의·아우터·원피스 각 5개로 균형을 유지했다. 관측 이력 없음·부족, 증가 확인, 장기 미관측, 최근 관측 시각을 선정에 활용하고 중복 선정과 실패 직후 반복 재시도를 방지했다.

**Validation.** 새로운 우선순위 방식은 테스트 및 운영 설정 적용까지 완료했다는 사용자 제공 이력을 반영했다. **최초 예약 실행의 실제 성과는 별도 검증 대상**이다. 이 저장소의 모니터링 숫자는 모두 가상이며 우선순위 방식의 효과를 입증하지 않는다. 공개 코드에는 systemd 타이머나 운영 선정 알고리즘을 복제하지 않았다.

**Trade-offs.** 균등 할당은 인기 카테고리의 단기 변화 포착량을 줄일 수 있다. 카테고리 내 후보가 부족할 때의 재배분 정책과 정확한 우선순위 가중치는 제공되지 않아 명세로 발명하지 않았다. 운영 효과는 관측 날짜 수·비교 커버리지·재시도 비용을 실행 전후 같은 창으로 비교해야 한다.

## Case Study 03 · Observation Quality Assessment

**Problem.** 리뷰 증가량이 있어도 관측 날짜·기간·최근성이 충분하지 않으면 결과를 해석하기 어려웠다.

**Root Cause.** 스냅샷 개수만 세면 같은 날의 반복 관측을 충분한 시계열처럼 오해할 수 있다. 마지막 유효 관측이 오래됐거나 추출이 실패한 경우 최신성이 과대평가될 수 있다.

**Solution.** 최근 7일의 고유 KST 날짜 수, 실제 관측 기간, 마지막 유효 관측 이후 시간을 함께 계산했다. 반복 관측은 3일·48h·72h 이내, 비교 가능은 2일·24h·72h 이내로 구분했다. 결측과 실제 0을 분리하고 각 등급의 근거를 BI에 노출했다.

**Validation.** 공개 데모에서 KST 자정 경계, 24·48·72시간 경계, 오래된·미래 관측, 결측, 중복이 등급을 왜곡하지 않는지 단위 테스트한다. 품질은 고정 7일 창, 트렌드는 선택 기간이라는 UI 규칙을 명시했다. 세부 정의는 [Data Quality Strategy](data-quality.md)를 따른다.

**Trade-offs.** 운영 규칙 기반 분류로 통계적 신뢰도를 추정하지 않는다. 상품별 노출·판매·구매 시점, 리뷰 작성 지연, 표본 선택 편향을 통제하지 않는다. ‘반복 관측’ 상품도 수요 증가나 시장 전체 경향을 증명하는 것은 아니다.

## 면접에서 설명할 수 있는 설계 판단

| 판단 | 설명할 근거 |
| --- | --- |
| 정확성 우선 추출 | 동일 상품 검증·유일한 후보·0과 결측 분리 |
| 시간 모델링 | 상품 메타데이터와 불변 관측 스냅샷의 역할 분리 |
| 수집 전략 | 수량뿐 아니라 카테고리 분포·관측 이력·재시도 비용 고려 |
| 해석 가능성 | delta와 관측 근거를 함께 노출하고 감소를 숨기지 않음 |
| 재현 가능한 공개 구현 | 합성 fixture, 고정 기준 시각, 표준 라이브러리, 테스트 |
